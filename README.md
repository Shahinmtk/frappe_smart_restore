# frappe_smart_restore
The frappe_smart_restore script is an automated, production-ready tool designed to safely restore Frappe/ERPNext backups while preventing database migration failures caused by missing custom applications.


Automatic Detection: It automatically locates the active Frappe bench directory, selects the target site, and identifies the latest matching database, public, and private file backups.

Pre-Restore Inspection: Before altering any data, the script scans the SQL backup file to identify applications that are registered in the backup but missing from the current server environment.

Dummy App Recovery: If missing apps are found, the script generates temporary "dummy apps" to satisfy Frappe's Python module import checks, allowing the initial database migration to pass without crashing.

Safe Registry Cleanup: Following the first migration, the script safely unlinks the missing applications using remove-from-installed-apps. This clears the app from the registry while preserving its underlying SQL data tables, unlike the destructive uninstall-app command which permanently deletes data.

End-to-End Automation: The workflow automatically handles pre-restore safety backups, full data restoration, two-stage migrations, and the final cleanup of the temporary dummy apps.

Setup & Installation
1. Save the final script as frappe_smart_restore.sh on your server.
2. Grant execution permissions by running: chmod +x frappe_smart_restore.sh.
3. Important: Execute the script as the designated frappe system user (e.g., su - frappe). Do not execute as root. (The script includes a safety check that will warn you if run as root).

Directory Structure & Backup Formats
The script expects to be run from inside the Frappe bench, preferably where your backups are stored.   
Sample working directory structure: 
/home/frappe/frappe-bench/backups/
├── 20261026_130000-site1.local-database.sql.gz
├── 20261026_130000-site1.local-private-files.tgz
└── 20261026_130000-site1.local-files.tgz

Supported Formats: .sql, .sql.gz for databases; .tar, .tar.gz, and custom .tgz for public/private files.

3. Usage & Restoration Examples
Navigate to your backup folder before running the script:
cd /home/frappe/frappe-bench/backups
Dry-Run Mode (Safe preflight check): Run ./frappe_smart_restore.sh --dry-run to output the site target, detected backups, and missing app report without modifying databases or files.

Database-only backup (Single Site): Execute ./frappe_smart_restore.sh. The script auto-detects the site, backup, and skips file restoration if only the SQL file is present.   

Full Backup with Missing Apps: Execute ./frappe_smart_restore.sh in a directory with all three backup files. The script detects missing app modules and asks for upfront configuration. Select Option 2 to use dummy apps, which allows the initial migration to safely pass.

4. App Removal Strategies Explained
When the script encounters missing applications, it offers two cleanup paths for the database registry:

Option A: uninstall-app (Destructive)
This executes the app's before_uninstall hooks and drops all SQL tables belonging to DocTypes defined in the app. Data is lost permanently.

Option B: remove_from_installed_apps (Safe)
This is non-destructive to data. It merely removes the application's string from the installed_apps array in tabDefaultValue and the tabModule Def table. The underlying SQL tables remain in MariaDB, allowing bench migrate to run without crashing on missing Python modules.

5. Limitations & Troubleshooting
Timestamp Parsing Errors: If backup files are rejected, ensure they adhere strictly to the YYYYMMDD_HHMMSS-site-database.sql.gz naming convention.   
Dummy-App Limitations: A dummy app generated by the script is completely blank. It satisfies Frappe's Python module import checks during bench migrate. However, it does not contain original schema migrations (patches), fixtures, or DocType JSONs.
Second Migration Failures: Review the generated timestamped log file. A Table missing error during the secondary migration indicates a hard dependency on the missing app's schema by a remaining application. In this case, dummy apps are insufficient and the original repository must be manually restored.
